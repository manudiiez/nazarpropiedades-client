# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev     # dev server (Turbopack) on http://localhost:3000
npm run build   # production build
npm run start   # serve the production build
npm run lint    # eslint (flat config, eslint-config-next core-web-vitals + typescript)
```

Type checking: `npx tsc --noEmit` (tsconfig is `noEmit`; there is no `typecheck` script).

There is no test framework installed — no test runner, no test files. Don't invent a test command; if tests are needed, pick and install a runner first and say so.

## State of the project

This is the `client` half of a real-estate site (NazarPropiedades). The **data layer is built** (`lib/domain`, `lib/data`, `lib/forms`, `lib/actions`) and tested — see "Capa de datos" below. The **UI is not**: `app/layout.tsx`, `app/page.tsx`, `app/globals.css` and the `public/*.svg` placeholders are still generated boilerplate. Treat anything in `app/` as replaceable rather than as established convention.

The API lives in the sibling `api` repo (FastAPI) and is a separate repository; this folder has no backend.

## Stack specifics that matter

- **Next.js 16.4.6 / React 19.3, App Router.** Per `AGENTS.md`, this Next version has breaking changes relative to older knowledge. Before writing routing, caching, or data-fetching code, read the relevant guide under `node_modules/next/dist/docs/01-app/` instead of relying on memory. `AGENTS.md` is regenerated by `next dev`, so leave that block alone.
- **`cacheComponents: true`** in `next.config.ts` — caching is explicit per component/function, and dynamic data access has to be handled deliberately. Check the docs for `use cache` semantics before adding fetches.
- **`partialPrefetching: true`** and `experimental.agentFeedback: true` are also enabled.
- **Tailwind CSS v4**, imported with `@import "tailwindcss"` in `app/globals.css` and compiled through the `@tailwindcss/turbopack` loader configured in `next.config.ts`. There is **no `tailwind.config.js` and no PostCSS config** — design tokens live in the `@theme inline` block in `globals.css`. Adding a Tailwind config file or a postcss pipeline would fight the existing setup.
- **Typed route props are global**: `app/layout.tsx` uses `LayoutProps<"/">`, generated by the Next TS plugin. Use `PageProps<"/route">` / `LayoutProps<...>` rather than hand-written props types.
- **Path alias** `@/*` maps to the project root (not `src/`), e.g. `@/app/...`.

## Capa de datos

Toda lectura y escritura contra la API pasa por `lib/data`. **Los componentes no hacen `fetch` ni conocen la URL de la API.**

```
lib/domain/      tipos del dominio, no saben de dónde vienen los datos
lib/data/
  queries.ts     ← lo único que importa la UI. Ninguna función lanza.
  failures.ts    ← traducción de cualquier error a algo mostrable
  index.ts       ← factory: elige implementación según DATA_SOURCE
  http/          ← implementación contra la API, con `use cache`
  mock/          ← implementación con fixtures, sin red
lib/filters/     traducción entre la URL del sitio y `ListingFilters`
lib/forms/       parseo de FormData y estado de formularios (sin Next, testeable)
lib/actions/     Server Actions
```

### Reglas

- **La UI importa de `lib/data/queries`**, no de `lib/data/http` ni de `lib/data/mock`.
- **Ninguna función de `queries.ts` lanza**: devuelven `DataResult<T>`, que es `{ok: true, data}` o `{ok: false, failure}`. La `failure` trae `title` y `message` en español, listos para mostrar.
- **Un listado vacío y un detalle inexistente NO son fallas**: son estados válidos (`items: []`, `data: null`). La UI muestra "no encontramos propiedades" o llama a `notFound()`.
- Las secciones accesorias (relacionadas, destacadas) usan `attemptOr` y degradan a `[]`: la página se muestra igual sin ese bloque. La falla igual se loguea.
- **Las opciones de los filtros salen de `getFacets()`**, nunca de listas en el front. El catálogo (`getCatalog()`) sirve para resolver etiquetas y para formularios donde hace falta el universo completo. Si una etiqueta está mal escrita, se corrige en la API.

### Trampas del contrato que ya costaron entender

- `price` y `expenses` llegan como **string** (`"845000.00"`), y los valores del JSONB también (`"bedrooms": "3"`). Los mappers los convierten; nada de esto llega como string al dominio.
- **El detalle no es un superconjunto del listado**: no trae `key_attributes` (lo reemplaza `attributes` enriquecido). Por eso `Listing` no extiende `ListingSummary`.
- `search` busca **solo** en barrio/calle y dirección, no en título ni descripción. En el dominio el campo se llama `addressQuery` para que la UI no prometa de más.
- `full_address` llega en MAYÚSCULAS; el mapper la normaliza.
- Provincia, departamento y zona son **slugs**; las etiquetas se resuelven contra el catálogo al mapear.
- `sort: "menor_precio"` ordena **mezclando monedas** (la API no convierte). Si se ordena por precio, conviene forzar una moneda.
- Sin resultados, `totalPages` es **0**, no 1: no hay que dibujar paginador.
- `fuente: "propiedad_individual"` **exige** `listingId` en el formulario de consultas.
- **Los `instanceof` no sobreviven a `use cache`**: React reconstruye el error y pierde las propiedades propias. En `failures.ts` se discrimina por `error.name`. No refactorizar a `instanceof`.

### Filtros en la URL

`lib/filters` traduce en los dos sentidos: `filtrosDesdeSearchParams(params, catalog)` → `{filtros, descartados}` y `searchParamsDesdeFiltros(filtros, pagina)` → `URLSearchParams`. Los nombres de los params están en `PARAMS`; la UI no escribe strings sueltos.

- **Los params están en español y no son los de la API** (`operacion`, `tipo`, `precio_max`, no `condition`, `property_type`, `price_max`). La URL se comparte por WhatsApp y la indexa Google: es parte del producto. La traducción a la API vive aparte, en `lib/data/http/filters-to-query.ts`.
- **Los enums que el front define traducen su valor** (`operacion=venta`, `antiguedad=a-estrenar`, `dormitorios=5-o-mas`). Los valores respaldados por el catálogo —tipo de propiedad, provincia, departamento, zona, amenities— **viajan con su slug** (`tipo=house`, `zona=chacras_de_coria`): son 16, 215 y 44 valores que cambian sin avisar, y un diccionario local para traducirlos es el bug de las amenities otra vez.
- **Multi-valor repetido, no separado por comas**: `?tipo=house&tipo=ph`.
- **Un valor inválido se ignora, nunca falla.** Es lo contrario de `validateFilters`, y es a propósito: una URL puede ser un link de hace un año. Lo descartado vuelve en `descartados` (`{param, valor, motivo}`) para poder avisar "ignoramos un filtro que ya no existe". Invariante: lo que sale de acá nunca hace lanzar a `validateFilters`.
- **Los defaults no se serializan**: `orden=reciente` y `pagina=1` se omiten, para que haya una sola URL por contenido. Al parsear, `sort` siempre queda definido (`reciente`), así una URL sin orden y otra con el orden por defecto dan el mismo objeto.
- **El tamaño de página no viaja en la URL.** `paginaDesdeSearchParams` devuelve siempre `limit: DEFAULT_PAGE_SIZE`: exponerlo sería `?limit=100` gratis y la misma lista en N URLs.
- `searchParams` es una API dinámica: **no se lee dentro de un scope con `use cache`**. La página la resuelve y le pasa el objeto a estas funciones, que son puras.

### Caché

`use cache` va en las funciones de los repositorios, **no en `HttpClient`**: los argumentos de una función cacheada tienen que ser serializables, y ni una instancia de clase ni un `AbortSignal` lo son.

- Catálogo: `cacheLife("hours")`, tag `catalogs`.
- Listings y facets: `cacheLife("minutes")` — revalida cada minuto —, tags `listings` / `facets`.

No es una optimización: la API limita a 60/min por IP y los pedidos del server cuentan contra la IP del server. **El caché es lo que evita el 429.**

Las 215 zonas del catálogo son una lista en el **código** de la API, no una tabla: el catálogo solo cambia cuando la API se despliega. Lo que cambia al cargar una propiedad son **facets** y el listado, que revalidan cada minuto.

Por eso los combos del filtro se arman con **facets, no con el catálogo**: si el CRM carga una propiedad con un slug de zona que no está en el catálogo de la API, no va a aparecer nunca en `/catalogs` pero sí en `/facets`, con su etiqueta derivada. Facets es la verdad sobre lo que hay publicado.

### Variables de entorno

| Variable | Para qué |
|---|---|
| `DATA_SOURCE` | `api` o `mock`. Sin valor válido, la app no arranca. |
| `API_URL` | URL de la API. Variable de **runtime**, no build-arg. |

**No hay ninguna `NEXT_PUBLIC_*`.** Ningún pedido sale del browser, ni el POST del formulario (va por Server Action reenviando la IP del visitante en `X-Forwarded-For`, para que el rate limit de la API cuente por visitante). Por eso la **misma imagen `vX.Y.Z` sirve staging y producción**.

Para trabajar sin backend: `DATA_SOURCE=mock npm run dev`.

### Tests

`npm test` (Vitest). La suite de contrato (`tests/contrato.test.ts`) corre la misma batería contra las dos implementaciones y compara **invariantes**, no cantidades. Los casos de la implementación HTTP se saltean si no hay API respondiendo, así que en CI pasan 188 y se saltean 29.

## Flujo de trabajo Git / GitHub

Este repo usa la skill **`flujo-github`** (`.claude/skills/flujo-github/SKILL.md`). Cargala **siempre** antes de hacer un commit, crear o leer issues, crear ramas, abrir PRs, promover ramas o crear tags de versión.

Lo esencial:

- Ramas permanentes: `develop` (por defecto, integración) → `testing` (staging, imagen `:testing`) → `main` (versiones con tags `vX.Y.Z`).
- Nunca push directo a `develop`, `testing` ni `main`. Nunca mergear PRs: los mergea el usuario.
- Las ramas de trabajo salen de `develop`: `feat/N-slug`, `fix/N-slug`, `chore/…`. PR a `develop` con `Closes #N`.
- Commits y títulos de PR en Conventional Commits, descripción en español e imperativo.
- Al empezar: `git config core.hooksPath` debe ser `.githooks`.

### Scopes de este repo

Front-end, todavía en scaffold. Scopes previstos a medida que aparezcan las secciones:

`propiedades` (listado, filtros, detalle), `home`, `contacto`, `tasaciones`, `nosotros`, `ui` (componentes compartidos), `layout` (header/footer/navegación), `seo` (metadata, sitemap, robots), `api` (clientes HTTP hacia la API), `config` (next.config, tsconfig, eslint), `docker`, `ci`, `deps`.

Si ninguno encaja, omitir el scope antes que inventar uno nuevo.

### Comandos

- Tests: `npm test` (Vitest). Con la API local levantada corren también los casos HTTP de la suite de contrato.
- Lint: `npm run lint`
- Tipos: `npx tsc --noEmit`
- Build: `npm run build`

### Imagen Docker

`Dockerfile` multi-stage con `output: "standalone"` (ver `next.config.ts`). **No tiene build-args de configuración**: como ningún pedido sale del browser, nada de la API queda horneado en el bundle y la imagen no está atada a un entorno. `API_URL` y `DATA_SOURCE` se pasan como variables del contenedor.

Si alguna vez hace falta una `NEXT_PUBLIC_*`, hay que declararla como `ARG`/`ENV` en el `Dockerfile` y como build-arg en los dos workflows — y aceptar que la imagen deja de servir para los dos entornos.
