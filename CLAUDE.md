# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev     # dev server (Turbopack) on http://localhost:3000
npm run build   # production build
npm run start   # serve the production build
npm run lint    # eslint (flat config, eslint-config-next core-web-vitals + typescript)
```

Type checking: `npx tsc --noEmit` (tsconfig is `noEmit`; there is no `typecheck` script).

There is no test framework installed — no test runner, no test files. Don't invent a test command; if tests are needed, pick and install a runner first and say so.

## State of the project

This is the `client` half of a real-estate site (NazarPropiedades). The **data layer is built** (`lib/domain`, `lib/data`, `lib/forms`, `lib/actions`) and tested — see "Capa de datos" below. The **UI is not**: `app/layout.tsx`, `app/page.tsx`, `app/globals.css` and the `public/*.svg` placeholders are still generated boilerplate. Treat anything in `app/` as replaceable rather than as established convention.

The API lives in the sibling `api` repo (FastAPI) and is a separate repository; this folder has no backend.

## Stack specifics that matter

- **Next.js 16.4.6 / React 19.3, App Router.** Per `AGENTS.md`, this Next version has breaking changes relative to older knowledge. Before writing routing, caching, or data-fetching code, read the relevant guide under `node_modules/next/dist/docs/01-app/` instead of relying on memory. `AGENTS.md` is regenerated by `next dev`, so leave that block alone.
- **`cacheComponents: true`** in `next.config.ts` — caching is explicit per component/function, and dynamic data access has to be handled deliberately. Check the docs for `use cache` semantics before adding fetches.
- **`partialPrefetching: true`** and `experimental.agentFeedback: true` are also enabled.
- **Tailwind CSS v4**, imported with `@import "tailwindcss"` in `app/globals.css` and compiled through the `@tailwindcss/turbopack` loader configured in `next.config.ts`. There is **no `tailwind.config.js` and no PostCSS config** — design tokens live in the `@theme inline` block in `globals.css`. Adding a Tailwind config file or a postcss pipeline would fight the existing setup.
- **Typed route props are global**: `app/layout.tsx` uses `LayoutProps<"/">`, generated by the Next TS plugin. Use `PageProps<"/route">` / `LayoutProps<...>` rather than hand-written props types.
- **Path alias** `@/*` maps to the project root (not `src/`), e.g. `@/app/...`.

## Capa de datos

Toda lectura y escritura contra la API pasa por `lib/data`. **Los componentes no hacen `fetch` ni conocen la URL de la API.**

```
lib/domain/      tipos del dominio, no saben de dónde vienen los datos
lib/data/
  queries.ts     ← lo único que importa la UI. Ninguna función lanza.
  failures.ts    ← traducción de cualquier error a algo mostrable
  index.ts       ← factory: elige implementación según DATA_SOURCE
  http/          ← implementación contra la API, con `use cache`
  mock/          ← implementación con fixtures, sin red
lib/filters/     traducción entre la URL del sitio y `ListingFilters`
lib/forms/       parseo de FormData y estado de formularios (sin Next, testeable)
lib/actions/     Server Actions
```

### Reglas

- **La UI importa de `lib/data/queries`**, no de `lib/data/http` ni de `lib/data/mock`.
- **Ninguna función de `queries.ts` lanza**: devuelven `DataResult<T>`, que es `{ok: true, data}` o `{ok: false, failure}`. La `failure` trae `title` y `message` en español, listos para mostrar.
- **Un listado vacío y un detalle inexistente NO son fallas**: son estados válidos (`items: []`, `data: null`). La UI muestra "no encontramos propiedades" o llama a `notFound()`.
- Las secciones accesorias (relacionadas, destacadas) usan `attemptOr` y degradan a `[]`: la página se muestra igual sin ese bloque. La falla igual se loguea.
- **Las opciones de los filtros salen de `getFacets()`**, nunca de listas en el front. El catálogo (`getCatalog()`) sirve para resolver etiquetas y para formularios donde hace falta el universo completo. Si una etiqueta está mal escrita, se corrige en la API.

### Trampas del contrato que ya costaron entender

- `price` y `expenses` llegan como **string** (`"845000.00"`), y los valores del JSONB también (`"bedrooms": "3"`). Los mappers los convierten; nada de esto llega como string al dominio.
- **El detalle no es un superconjunto del listado**: no trae `key_attributes` (lo reemplaza `attributes` enriquecido). Por eso `Listing` no extiende `ListingSummary`.
- `search` busca **solo** en barrio/calle y dirección, no en título ni descripción. En el dominio el campo se llama `addressQuery` para que la UI no prometa de más.
- `full_address` llega en MAYÚSCULAS; el mapper la normaliza.
- Provincia, departamento y zona son **slugs**; las etiquetas se resuelven contra el catálogo al mapear.
- `sort: "menor_precio"` ordena **mezclando monedas** (la API no convierte). Si se ordena por precio, conviene forzar una moneda.
- Sin resultados, `totalPages` es **0**, no 1: no hay que dibujar paginador.
- `fuente: "propiedad_individual"` **exige** `listingId` en el formulario de consultas.
- **Los `instanceof` no sobreviven a `use cache`**: React reconstruye el error y pierde las propiedades propias. En `failures.ts` se discrimina por `error.name`. No refactorizar a `instanceof`.

### Formateo

Precios, superficies, atributos y fechas se formatean en `lib/format`, con funciones puras. **Ningún componente formatea números por su cuenta**: si eso se duplica, cada sección termina con su propio criterio.

- **La moneda nunca se muestra sin su símbolo o código, y nunca se convierte.** La API no convierte, y hacerlo acá implicaría una cotización que nadie mantiene. USD va como `USD 320.000`, ARS como `$ 450.000`, sin decimales.
- **Un alquiler lleva "por mes"** (`formatearPrecioPorMes`, que usa `isRental`): mostrar un alquiler como precio total es un error de lectura caro.
- **Un precio en 0 no es un precio**: se muestra `Consultar precio`, porque "$ 0" parece un error del sitio.
- **Lo que no se puede mostrar devuelve `null`**, no `""`: así el componente no dibuja la línea en lugar de dibujarla vacía. Vale para las expensas ausentes y para los atributos sin valor.
- **El sufijo lo manda la API** en cada atributo; no se inventa. El `0` y los booleanos se muestran (`Sí`/`No`): "sin cochera" es un dato, no ausencia de dato.
- **Las claves de `keyAttributes` varían por propiedad** y el tipo es `Partial`: todo formateador que las consuma maneja `undefined`, que es el caso normal.
- **La hora no se lee en el render de un componente.** `new Date()` durante el prerender rompe con `blocking-prerender-current-time`: Next descarta el intento y vuelve a renderizar la ruta entera (apareció en el log con el listado y la ficha ya hechos). La página declara el acceso dinámico con `await connection()`, lee la hora una vez y la baja por props; por eso `formatearFecha` y `formatearPublicacion` reciben `ahora`.
- **Las fechas van relativas hasta 30 días** y absolutas después: nadie lee "hace 237 días". `formatearFecha` recibe `ahora` como parámetro para poder testearlo. Ojo: en español `numeric: "auto"` devuelve "ayer" y "anteayer", no solo "hace N días", así que la preposición de "Publicado …" no se puede decidir con un `startsWith("hace")`.

### Filtros en la URL

`lib/filters` traduce en los dos sentidos: `filtrosDesdeSearchParams(params, catalog)` → `{filtros, descartados}` y `searchParamsDesdeFiltros(filtros, pagina)` → `URLSearchParams`. Los nombres de los params están en `PARAMS`; la UI no escribe strings sueltos.

- **Los params están en español y no son los de la API** (`operacion`, `tipo`, `precio_max`, no `condition`, `property_type`, `price_max`). La URL se comparte por WhatsApp y la indexa Google: es parte del producto. La traducción a la API vive aparte, en `lib/data/http/filters-to-query.ts`.
- **Los enums que el front define traducen su valor** (`operacion=venta`, `antiguedad=a-estrenar`, `dormitorios=5-o-mas`). Los valores respaldados por el catálogo —tipo de propiedad, provincia, departamento, zona, amenities— **viajan con su slug** (`tipo=house`, `zona=chacras_de_coria`): son 16, 215 y 44 valores que cambian sin avisar, y un diccionario local para traducirlos es el bug de las amenities otra vez.
- **Multi-valor repetido, no separado por comas**: `?tipo=house&tipo=ph`.
- **Un valor inválido se ignora, nunca falla.** Es lo contrario de `validateFilters`, y es a propósito: una URL puede ser un link de hace un año. Lo descartado vuelve en `descartados` (`{param, valor, motivo}`) para poder avisar "ignoramos un filtro que ya no existe". Invariante: lo que sale de acá nunca hace lanzar a `validateFilters`.
- **Los defaults no se serializan**: `orden=reciente` y `pagina=1` se omiten, para que haya una sola URL por contenido. Al parsear, `sort` siempre queda definido (`reciente`), así una URL sin orden y otra con el orden por defecto dan el mismo objeto.
- **El tamaño de página no viaja en la URL.** `paginaDesdeSearchParams` devuelve siempre `limit: DEFAULT_PAGE_SIZE`: exponerlo sería `?limit=100` gratis y la misma lista en N URLs.
- `searchParams` es una API dinámica: **no se lee dentro de un scope con `use cache`**. La página la resuelve y le pasa el objeto a estas funciones, que son puras.

### Listado `/propiedades`

`app/propiedades/page.tsx` es la primera ruta que consume la capa de datos. `app/propiedades/consulta.ts` traduce la URL una sola vez (`resolverConsulta`) y los componentes de `components/propiedades/` solo renderizan.

- **La página no hace `await` de nada.** La cáscara se prerenderiza estática y todo lo que depende de `searchParams` va en `<Suspense>`; si no, el build falla con `blocking-prerender-dynamic`. Son **dos boundaries**: los filtros salen de lecturas cacheadas y llegan antes que los resultados. `resolverConsulta` se llama una vez y la **misma promesa** se le pasa a las dos secciones, así el parseo y las lecturas no se hacen dos veces.
- **Las opciones de los combos salen de `getFacets()`**; el catálogo es el respaldo cuando facets falla (filtro sin conteos antes que sin filtro) y la **única** fuente de las amenities, que facets no trae. Las opciones con `count: 0` van deshabilitadas **con** su conteo; si el valor venía marcado en la URL, no se deshabilita: hay que poder destildar el filtro que dejó la lista en cero.
- **El submit es una Server Action (`lib/actions/filtros.ts`), no un `<form method="get">`.** Un form GET manda también los campos vacíos, así que buscar sin tocar nada deja `?direccion=&precio_min=&…`: dos URLs para la misma lista, y la URL es parte del producto. La acción hace FormData → filtros → URL canónica → `redirect`. Funciona sin JavaScript (POST + 303).
- **Ubicación progresiva**: provincia → departamentos de esa provincia → zonas de los departamentos elegidos. Las 215 zonas juntas no son un filtro, y cada submit trae el nivel siguiente, así que tampoco necesita JavaScript.
- **Ordenar por precio fuerza una moneda** (`lib/filters/orden.ts`), elegida entre las que tienen publicaciones según `facets.priceRange`. La moneda forzada **viaja en la URL** y se avisa al lado del control: así el link compartido reproduce la lista que se vio.
- **Las etiquetas de los controles que el front define** (antigüedad, "5 o más", orden, secciones de amenities) están en `lib/filters/opciones.ts`, y su `value` se calcula con los mismos codificadores que `searchParamsDesdeFiltros` (`EN_URL`). Un diccionario aparte en el componente se desincroniza y el filtro se dibuja bien pero no filtra.
- **Tres pantallas vacías distintas, y confundirlas miente**: una falla de datos (`FallaDeDatos`, con reintentar), cero resultados (`SinResultados`, con los filtros aplicados para saber qué soltar) y una página más allá del final (`PaginaFueraDeRango`, porque sí hay resultados, están en la página 1).
- **La tarjeta usa `coverPhoto.url`, no `thumbnailUrl`**: la miniatura mide 400x300 y `w=400` no es un ancho permitido. `coverPhoto` puede ser `null` con la propiedad publicada (el worker de imágenes todavía no corrió): va un placeholder.

### Detalle `/propiedad/[id]/[[...slug]]`

La ficha. Es la página que indexa Google y la que se comparte, así que las decisiones son distintas a las del listado.

- **La URL canónica es `/propiedad/{id}/{slug}` y el slug es decorativo.** La API no tiene slug: lo único que identifica la propiedad es el id. El slug se arma en `lib/format/propiedad.ts` a partir del **título compuesto** (tipo + operación + zona) y **no** de `title`, que el CRM edita: si dependiera de `title`, cambiarlo movería la URL de una propiedad ya compartida. El segmento es un catch-all **opcional** para que `/propiedad/{id}` resuelva —los `sibling_listings` llegan sin tipo ni ubicación y no pueden armar el slug— y redirija al canónico.
- **El contenido va en un `<Suspense>`.** Sin boundary, el HTML sale con la cáscara vacía y la ficha entera se renderiza en el cliente desde el payload de RSC (verificado: 59 KB de HTML con boundary, 13 KB sin él). En esta página eso no es un detalle.
- **`notFound()` no devuelve un 404 de HTTP.** Con `cacheComponents` la respuesta arranca con 200 en cuanto sale la cáscara; lo que mantiene la URL fuera del índice es el `<meta name="robots" content="noindex">` que Next agrega en el stream. Un 404 duro exigiría chequear en Proxy, y ahí no se sabe si el id existe sin pedirle la propiedad a la API en cada request. Mismo mecanismo para el redirect del slug, que viaja en el stream.
- **`showMap` manda sobre las coordenadas**: con `showMap: false` no se dibuja mapa aunque haya lat/lng. Y con `mode` distinto de `exact` **no se publican las coordenadas ni un link al punto**: el propietario pidió que se muestre el área, y filtrar el punto por la ventana del mapa es lo mismo que publicarlo. `range` es el radio en metros.
- **Los booleanos del JSONB llegan capitalizados como en Python** (`"True"`, no `"true"`): sin eso la ficha mostraba "Piscina: True". Se convierten en el mapper.
- **Algunos atributos traen el valor del enum en crudo** (`garage_type: "garage_doble"`). La etiqueta y el sufijo sí vienen listos, pero el valor no tiene endpoint que lo traduzca: `lib/format/atributos.ts` normaliza solo lo que tiene pinta de slug (todo minúscula, sin espacios) para no tocar lo que el CRM escribió a mano. Lo correcto es que la API mande la etiqueta del valor.
- **Los nombres de las secciones los pone el front** (`lib/format/secciones.ts`), porque la API manda la clave (`dimensions`, `amenities_comfort`) y no hay endpoint que devuelva su nombre. Es la única excepción a "las etiquetas vienen de la API", y una sección desconocida se degrada con `humanize`. El orden de las secciones es el de la respuesta: la API ya ordena por prioridad.
- Los tres bloques de atributos (`attributes`, `amenities`, `nearbyZones`) **pueden venir vacíos** si no hay strategy para ese par (tipo, condición): cada bloque decide no dibujarse. Las relacionadas van en su propio `<Suspense>` y degradan a nada.

### Home

`app/page.tsx`: buscador rápido, accesos a las búsquedas más comunes, destacadas y el formulario de consulta general.

- **Los bloques con datos se resuelven por request (`await connection()` antes de leer), aunque las lecturas estén cacheadas.** Parece contradecir que la home sea cacheable, y es por el Dockerfile: la imagen se construye **sin `DATA_SOURCE`** (ninguna variable de la API es build-arg, para que la misma imagen sirva staging y producción), así que en el build las lecturas fallan y degradan a vacío. Si los bloques se prerenderizaran, la cáscara quedaría horneada con cero destacadas y sin conteos **y así se serviría siempre**. Verificado: construyendo sin `DATA_SOURCE` y levantando con `DATA_SOURCE=mock`, la home servía la cáscara vacía en todos los requests. No cuesta pedidos extra: el caché sigue en los repositorios, que es lo que protege del rate limit.
- **Las destacadas salen de `getFeaturedListings()`**, no de `getLatestListings()`, aunque hoy devuelvan lo mismo: cuando la API tenga `featured` cambia esa función y la home no se toca. Usa `attemptOr`, así que una falla degrada a `[]` y la home se muestra sin el bloque.
- **Los accesos rápidos son links con los filtros en la URL** (`urlDelListado`), no botones: funcionan sin JavaScript, se comparten y los indexa Google. Los conteos salen de facets; si la lectura falla, van sin conteo.
- Las tres operaciones se ofrecen siempre, incluso con `count: 0` —esconder "Alquiler" hace parecer que la inmobiliaria no alquila—, pero un **departamento** con 0 no se ofrece: ahí el 0 no informa nada y el link promete una lista vacía.
- El `<Suspense>` de las destacadas va con `fallback={null}`: el bloque puede terminar vacío, y sin JavaScript un "Cargando…" se queda pegado donde no va a aparecer nada.

### Formulario de consulta

`components/formulario-de-consulta.tsx` usa la Server Action de `lib/actions/consultas.ts`. Dos usos con el mismo componente: la consulta general y la de una propiedad (`fuente="propiedad_individual"` + `listingId`, que la API **exige** en ese caso).

- **La confirmación es un redirect, no solo el estado del formulario.** Con `cacheComponents`, la respuesta de un POST trae la cáscara en HTML y el estado nuevo **solo en el payload de RSC**, para que lo aplique el cliente. Verificado: sin JavaScript, un envío correcto creaba la consulta y devolvía el formulario igual que antes — ni confirmación, ni datos, ni aviso. Por eso la action hace **POST → 303 → GET** con `?consulta=enviada`, que además evita que recargar reenvíe la consulta. El `permalink` de `useActionState` no alcanza: se probó y no cambia nada.
- **El destino del redirect viene del formulario, o sea del visitante**: `destinoDeConfirmacion` acepta solo rutas internas. Sin ese chequeo, `volverA=https://sitio-malo` convierte al formulario en un redirector abierto, que es phishing gratis con nuestro dominio.
- **Los atributos nativos (`required`, `type`, `pattern`, `maxLength`) duplican a propósito las reglas de `validateInquiry`**: son lo único que marca un campo mal cargado cuando no hay JavaScript, porque los errores por campo del server llegan por el payload de RSC y no se renderizan. Los del server son los que mandan, porque el endpoint es público.
- `useId` para los ids: el formulario de una propiedad y el general pueden convivir en la misma página, y dos inputs con el mismo id rompen la asociación del `<label>`.

### Metadata y SEO

`lib/seo` arma los títulos, las descripciones y los datos estructurados; cada ruta los usa en su `generateMetadata`.

- **`SITE_URL` es variable de runtime y se lee con `getSiteUrl()`, no con `getConfig()`**: `getConfig()` exige `DATA_SOURCE` y la metadata del layout se evalúa durante el build, que corre sin variables. Si falta, la metadata sale sin `metadataBase` en vez de romperse.
- **La metadata de una página prerenderizada se hornea en el build.** La home quedaba con `og:image` apuntando a `http://localhost:3000/opengraph-image` (el default de Next sin `metadataBase`), porque en el build no hay `SITE_URL`. Se arregla con `await connection()` en su `generateMetadata`. El listado y la ficha no tenían el problema: su metadata ya se genera por request.
- **El tipo de propiedad no se pluraliza en los títulos.** Las etiquetas vienen del catálogo y el plural en español no es agregar una "s" (`Local comercial` → `Local comerciales`, `PH` → `PHs`). Sin un tipo único, el título dice "Propiedades".
- **`noindex, follow` en los filtros profundos** (precio, superficie, ambientes, amenities, dirección, orden distinto del default, multi-valor, página > 1). `follow` igual: no se indexa la URL, pero las fichas se descubren desde cualquier listado.
- **Las coordenadas del JSON-LD siguen la misma regla que el mapa**: solo con `showMap` y `mode: "exact"`. Publicar el punto en los datos estructurados cuando la UI muestra el área es filtrarlo por JSON.
- **El JSON-LD se escapa con `jsonLdAHtml`**: la descripción la escribe el CRM, y un `</script>` ahí adentro cierra la etiqueta. Es XSS almacenado, no un detalle de formato.
- **`app/sitemap.ts` y `app/robots.ts` se generan por request (`await connection()`).** Si no, se prerenderizan en el build —sin variables— y quedan horneados: el robots.txt decía `Disallow: /` para siempre y producción no se indexaba nunca. Verificado con el contenedor levantado con `APP_ENV=production`.
- **Staging no se indexa**: con `APP_ENV` distinto de `production`, el robots.txt devuelve `disallow: /` y el sitemap sale vacío. El default es "no es producción": si falta la variable lo peor que pasa es que el sitio no se indexe —se ve en `/robots.txt`—, en vez de indexar staging en silencio y competir con el sitio real.
- **El robots.txt NO bloquea los listados con filtros**, aunque el issue #37 lo proponía: esas URLs ya salen con `noindex, follow`, y un `Disallow` impide que Google LEA ese noindex. Las dos cosas juntas se estorban.
- **Next no escapa el `&` de la query string en el sitemap**, así que una URL con filtros rompe el XML y Google lo rechaza entero. Se escapa en `lib/seo/sitemap.ts` antes de dárselo a Next; si alguna vez Next lo arregla, el test de `escaparParaXml` es el que avisa.
- **El sitemap enumera paginando el listado** (la API no tiene endpoint de ids), de a 100 y con tope de 20 pedidos, cacheado con `cacheLife("hours")`: lo pide un crawler, no un visitante. Si el tope queda corto, la solución es pedirle a la API un endpoint de ids, no subirlo.
- **`lastModified` se omite**: el dominio tiene `createdAt` pero no fecha de modificación, y mandar la de creación le miente a Google sobre la frescura. Cuando la API exponga `updated_at`, va ahí.
- La imagen por defecto de Open Graph la genera `app/opengraph-image.tsx` con `next/og`, que es parte de Next: no hay un PNG en `public/` que mantener. Cuando haya diseño, se reemplaza ahí.

### Caché

`use cache` va en las funciones de los repositorios, **no en `HttpClient`**: los argumentos de una función cacheada tienen que ser serializables, y ni una instancia de clase ni un `AbortSignal` lo son.

- Catálogo: `cacheLife("hours")`, tag `catalogs`.
- Listings y facets: `cacheLife("minutes")` — revalida cada minuto —, tags `listings` / `facets`.

No es una optimización: la API limita a 60/min por IP y los pedidos del server cuentan contra la IP del server. **El caché es lo que evita el 429.**

Las 215 zonas del catálogo son una lista en el **código** de la API, no una tabla: el catálogo solo cambia cuando la API se despliega. Lo que cambia al cargar una propiedad son **facets** y el listado, que revalidan cada minuto.

Por eso los combos del filtro se arman con **facets, no con el catálogo**: si el CRM carga una propiedad con un slug de zona que no está en el catálogo de la API, no va a aparecer nunca en `/catalogs` pero sí en `/facets`, con su etiqueta derivada. Facets es la verdad sobre lo que hay publicado.

### Imágenes

Las fotos vienen del bucket de Cloudflare R2 de la API, y el host está declarado en `images.remotePatterns` de `next.config.ts`. **Sin eso `next/image` responde 400 y no se ve ninguna foto**, con un error que apunta al componente y no a la configuración.

- El host es el mismo en los tres entornos; lo que cambia es el prefijo del key, que sale de `APP_ENV` en la API: `production` / `development` / `local`. Los tres están declarados, cada uno limitado a `/{entorno}/properties/**`. Nada de comodines: un `remotePatterns` abierto convierte al sitio en un optimizador de imágenes gratis para cualquiera.
- `remotePatterns` se evalúa **en build**, no en runtime. Si el bucket llegara a cambiar por entorno, la misma imagen Docker deja de servir para los dos.
- **La miniatura mide 400x300 y `400` no es un ancho permitido** por los `imageSizes`/`deviceSizes` por defecto de Next: pedirla con `w=400` da 400 Bad Request. Para las tarjetas hay que dejar que Next elija (`sizes`) o usar `384`.
- `thumbnail_url` puede ser `null`, y `cover_photo` puede ser `null` con `photos: []` aunque la propiedad sea válida: el worker de imágenes todavía no terminó. El componente tiene que mostrar un placeholder, no romperse.

### Errores en la UI

Tres boundaries en `app/`, y un componente para las fallas de datos:

| Archivo | Cubre |
|---|---|
| `app/error.tsx` | Bugs de render en cualquier ruta. Client Component (lo exige Next). |
| `app/global-error.tsx` | Un error en el layout raíz. Trae sus propios `<html>`/`<body>`. |
| `app/not-found.tsx` | Los `notFound()` y las URLs que no matchean ninguna ruta. |
| `components/falla-de-datos.tsx` | Un `DataResult` con `ok: false`. |

- **En Next 16 el prop del boundary es `retry`, no `reset`** (`reset` existe pero solo limpia el estado sin volver a pedir), y **`error` viene tipado `unknown`**: lo que se lanza en un Client Component viaja tal cual y puede no ser un `Error`. Hay que angostarlo.
- **No se muestra nunca el `message` del error.** En producción el de un Server Component ya es genérico, pero **en desarrollo llega el original**, con rutas y URLs internas. Lo que se loguea del lado del cliente es `error.digest` (`lib/ui/errores.ts`): es lo único que correlaciona lo que vio el visitante con el log del server.
- **Reintentar solo cuando sirve.** En los boundaries es `retry()`. En una falla de datos, en cambio, no hubo excepción: la página renderizó y la lectura devolvió `{ok: false}`, así que hay que volver a pedir los datos con `router.refresh()` (`components/boton-reintentar.tsx`, el único componente de cliente de esa pantalla). Si `failure.retryable` es `false`, no se ofrece el botón: reintentar devuelve lo mismo.
- **`global-error` no recibe los estilos globales** y no puede exportar `metadata`: de ahí los estilos inline y el `<title>` de React. No es desprolijidad.
- Un listado vacío y un detalle inexistente **no** son errores: `items: []` y `data: null` se resuelven con "no encontramos propiedades" o `notFound()`.

### Prerender bloqueante (`instant`)

Con `cacheComponents`, una ruta que bloquea esperando datos dinámicos **falla el build** con `blocking-prerender-dynamic`. Las salidas son envolver la parte dinámica en un `<Suspense>` (que es lo que conviene para una página de verdad) o declarar `export const instant = false` en la ruta. Apareció al probar los boundaries con rutas dinámicas; va a volver a aparecer en el listado y el detalle.

### Variables de entorno

| Variable | Para qué |
|---|---|
| `DATA_SOURCE` | `api` o `mock`. Sin valor válido, la app no arranca. |
| `API_URL` | URL de la API. Variable de **runtime**, no build-arg. |
| `SITE_URL` | URL pública del sitio, para las canónicas y el Open Graph. Runtime. Sin ella, lo que se comparte no resuelve la imagen. |
| `APP_ENV` | `production` habilita la indexación (robots + sitemap). Cualquier otro valor, o ausente, la bloquea. Mismo nombre que en la API. |

**No hay ninguna `NEXT_PUBLIC_*`.** Ningún pedido sale del browser, ni el POST del formulario (va por Server Action reenviando la IP del visitante en `X-Forwarded-For`, para que el rate limit de la API cuente por visitante). Por eso la **misma imagen `vX.Y.Z` sirve staging y producción**.

Para trabajar sin backend: `DATA_SOURCE=mock npm run dev`.

### Tests

`npm test` (Vitest). La suite de contrato (`tests/contrato.test.ts`) corre la misma batería contra las dos implementaciones y compara **invariantes**, no cantidades. Los casos de la implementación HTTP se saltean si no hay API respondiendo, así que en CI pasan 188 y se saltean 29.

## Flujo de trabajo Git / GitHub

Este repo usa la skill **`flujo-github`** (`.claude/skills/flujo-github/SKILL.md`). Cargala **siempre** antes de hacer un commit, crear o leer issues, crear ramas, abrir PRs, promover ramas o crear tags de versión.

Lo esencial:

- Ramas permanentes: `develop` (por defecto, integración) → `testing` (staging, imagen `:testing`) → `main` (versiones con tags `vX.Y.Z`).
- Nunca push directo a `develop`, `testing` ni `main`. Nunca mergear PRs: los mergea el usuario.
- Las ramas de trabajo salen de `develop`: `feat/N-slug`, `fix/N-slug`, `chore/…`. PR a `develop` con `Closes #N`.
- Commits y títulos de PR en Conventional Commits, descripción en español e imperativo.
- Al empezar: `git config core.hooksPath` debe ser `.githooks`.

### Scopes de este repo

Front-end, todavía en scaffold. Scopes previstos a medida que aparezcan las secciones:

`propiedades` (listado, filtros, detalle), `home`, `contacto`, `tasaciones`, `nosotros`, `ui` (componentes compartidos), `layout` (header/footer/navegación), `seo` (metadata, sitemap, robots), `api` (clientes HTTP hacia la API), `config` (next.config, tsconfig, eslint), `docker`, `ci`, `deps`.

Si ninguno encaja, omitir el scope antes que inventar uno nuevo.

### Comandos

- Tests: `npm test` (Vitest). Con la API local levantada corren también los casos HTTP de la suite de contrato.
- Lint: `npm run lint`
- Tipos: `npx tsc --noEmit`
- Build: `npm run build`

### Imagen Docker

`Dockerfile` multi-stage con `output: "standalone"` (ver `next.config.ts`). **No tiene build-args de configuración**: como ningún pedido sale del browser, nada de la API queda horneado en el bundle y la imagen no está atada a un entorno. `API_URL` y `DATA_SOURCE` se pasan como variables del contenedor.

Si alguna vez hace falta una `NEXT_PUBLIC_*`, hay que declararla como `ARG`/`ENV` en el `Dockerfile` y como build-arg en los dos workflows — y aceptar que la imagen deja de servir para los dos entornos.
